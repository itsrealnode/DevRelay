# База данных, фоновые задачи и побочные эффекты

Раздели три наблюдения: ответ вызывающей стороне, зафиксированные данные, внешний эффект. Статус 200 может соседствовать с потерянной записью. Мок отправщика может показать одну попытку, но не подтвердит доставку получателю. В отчёте назови границу проверки.

- **Несколько записей.** Вызови контролируемый сбой между первым и вторым изменением. Дай транзакции завершиться, прочитай БД через новую сессию или соединение. Проверь и отсутствие внешней отправки, если это гарантируется при откате.
- **Повтор.** Выполни операцию с тем же ключом после успешного сохранения и условной потери ответа. Проверь число бизнес-записей, событий истории и запланированных отправок. Включи второй законный вызов с другим ключом, когда это помогает обнаружить слишком широкую дедупликацию.
- **Гонка.** Запусти две попытки через разные соединения к одной тестовой БД. Для ошибки «оба прочли свободный остаток» воспроизведи именно этот порядок. Один одновременный старт допускает и полностью последовательное выполнение. Проверь, что корректная сериализация остаётся возможной. Если первый участник уже держит блокировку, ожидание второго внутри того же участка может повесить сам тест. Дождись обоих исходов и проверь по отдельному чтению количество записей и их владельцев. Если победитель может быть любым, сопоставь его с фактическим успешным ответом. На SQLite нельзя подтвердить поведение блокировок PostgreSQL. Если рабочая СУБД недоступна, укажи, что именно осталось непроверенным.
- **Фоновая работа.** Проверь отдельно постановку задачи, обработку и повтор после временного сбоя. Для системы с лимитом попыток проверь последнюю разрешённую попытку и состояние после исчерпания лимита. Для обязательной доставки проверь разрыв между коммитом и отправкой, когда это часть контракта.
- **Существующие данные.** Подготовь запись в форме, в которой она могла существовать до изменения. Пройди обычный путь чтения или обновления. Если план включает миграцию, проверь переход на изолированной БД проекта.

Для состояния с историей проверяй не только счётчик. Сверь владельца, тип события и ID записи с объектом, к которому относятся действия. Так тест заметит и побочный эффект, созданный для неправильного объекта.
