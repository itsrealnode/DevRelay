# Как запускать, фиксировать дефект и перепроверять

Найди команды и окружение в проекте. Сначала запусти ближайшие проверки, затем относящиеся к изменению регрессии. Изолируй данные и подменяй только внешнюю границу, которая не является предметом проверки. Для поведения ORM используй тестовую БД, для API — штатный клиент приложения. Производственные сервисы и пользовательские записи не являются тестовой фикстурой.

При добавлении регрессионного теста помести его рядом с тестами соответствующего пути. Для нестабильного падения сохрани вход, порядок запуска, seed при генерации и состояние данных. Повтори кейс отдельно и в исходной последовательности. При гонке управляй порядком сигналом или барьером с таймаутом, учти исключения каждого участника. Повторный зелёный запуск сам по себе оставляет причину открытой.

У каждой проверки должен быть один из наблюдаемых итогов: прошла, выявила дефект, заблокирована окружением или ещё не запущена. При сбое установки зависимостей не записывай кейсы как провал продукта. Если вместо внешнего API использована подмена, укажи, что доказано на этом уровне.

**Передача дефекта.** Приведи требование, исходное состояние, точный запрос или команду, ожидаемый результат, фактический результат и состояние после вызова. Приложи имя падающего теста либо минимальную последовательность воспроизведения. Удали секреты и персональные данные из примера. Включи дефект в результат проверки и сохрани регрессионный тест на согласованный контракт, если задача предусматривает изменение тестов.

После исправления запусти тот же кейс, а также близкие сценарии, которые могла задеть правка. После исправления очистки поля повтори проверку пропуска этого поля. В финале сопоставь критерии с результатами и фактическими командами. Укажи версию или состояние кода, на котором запускались тесты. В самостоятельном вызове верни результат пользователю, в полном цикле - координатору.
