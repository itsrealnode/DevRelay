# Проверка силы автотеста

Для критичного обещания назови реалистичную поломку и конкретный assert, который должен упасть. Например, обработчик ответил успешно, но записал новое значение соседнему объекту. В таком тесте понадобятся два различимых объекта, отдельное чтение после вызова и проверка владельца изменения.

При аудите пройди путь от фикстуры через штатную точку входа до утверждений. Обрати внимание на три способа получить ложный успех.

- Фикстура уже в ожидаемом состоянии. Задай отличимые прежнее и новое значения. Для запрета изменения положи реальные данные в защищаемое поле и проверь их сохранность.
- Результат вычислен тем же кодом либо повторяет ответ мока. Возьми ожидаемое значение из контракта. Читай фактический результат на границе обещания. Подтверждение вызова отправщика годится для обещания «передали на отправку». Для обещания «сохранили» перечитай запись.
- Слабое утверждение пропускает нарушение. Для выдачи двух конкретных объектов сравни идентификаторы и принадлежность. Для однократного эффекта проверь итог после повторной обработки. Один HTTP-статус или длина списка различают лишь часть исходов.

Для регрессии по возможности запусти один и тот же тест на версии с дефектом и на исправленной версии. Прочитай причину падения. Ошибка импорта, настройки или фикстуры не подтверждает воспроизведение. Сохрани команду, нарушенное утверждение и наблюдённые значения.

Если версии с дефектом нет, а обещание критично, можно проверить чувствительность теста в одноразовой копии. Запусти тест на исходной копии, внеси одну характерную ошибку в реализацию и повтори неизменённый тест. Правки остаются только в копии. Если обе версии зелёные, уточни вход или утверждение. Если воспроизвести поломку нельзя, сообщи, какую проверку выполнил и какая часть доказательства осталась открытой.
