# Сверка API и полей

Начни с публичного контракта затронутого маршрута: метод, путь, участник, способ передачи данных, статус, тело и доступные поля. Если в проекте есть OpenAPI, сравни схему с принятой постановкой и реальным ответом. Когда схема и поведение расходятся, покажи оба результата.

| Свойство поля | Какие входы различить | Что проверить |
|---|---|---|
| Обязательность и null | Ключ отсутствует, ключ равен null, передано допустимое значение | Статус, публичная ошибка или значение по умолчанию и факт записи. |
| Тип и диапазон | Допустимые границы, значение сразу снаружи, неверный тип | Согласованная нормализация или отказ, отсутствие частичной записи. |
| Пустое значение | Пустая строка, пустая коллекция, 0, false, если поле их допускает | Значимое значение не теряется при проверке истинности. |
| Доступ и назначение | Разные участники, read-only или внутреннее поле, если это описано | Право изменения, отсутствие лишних полей в выдаче и сохранность чужой записи. |
| Представление | Алиас, тип идентификатора, дата, точность числа или вложенная коллекция | Формат реального ответа и соответствие сохранённому значению. |

**Пример частичного обновления.** Создай профиль с отличимыми заполненными именем и городом. Отправь по очереди изменение одного поля, явный null для очищаемого поля и пустой объект, каждый раз с известным исходным состоянием. Проверь статус, значения в ответе и результат отдельного чтения. Изменение города не должно незаметно стереть имя. Если запись отклонена, проверь, что оба исходных значения на месте.

Для списка при наличии требований проверь фильтр, порядок, границы страниц и область видимости данных. Для ответа об ошибке сравни только гарантированные публичные поля. Привязывайся к точной формулировке текста ошибки лишь тогда, когда эта формулировка входит в контракт.
