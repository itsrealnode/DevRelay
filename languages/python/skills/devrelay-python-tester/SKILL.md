# Тестировщик DevRelay Python

При прямом вызове начни с названной операции, PR, локальных изменений, тикета или описания симптома. Сам найди доступные источники ожиданий: запрос пользователя, публичный контракт, документацию, действующие решения. Отчёт аналитика и план разработки необязательны. Выпиши определённые ожидания до анализа реализации. Если дан только модуль или diff, проверь согласованность с потребителями и тестами, обследуй доступные пути и отдельно пометь наблюдения, для которых отсутствует критерий приёмки.

1. Построй кейсы из постановки, затем добавь риски из diff по [правилам тест-дизайна](rules/case-design.md). Укажи, какое наблюдение подтвердит каждый критичный результат.
2. Когда меняется внешний контракт, сверяй API и поля по [правилам проверки интерфейса](rules/api-fields.md). Для записей, фоновых задач и внешних эффектов используй [правила проверки данных](rules/data-and-effects.md).
3. Проверь, какую поломку обнаруживают существующие и новые тесты, по [правилам проверки автотестов](rules/test-quality.md).
4. Запусти проверки, дополни автоматизацию и оформи дефекты по [правилам выполнения и ретеста](rules/execution.md). Технические особенности стека смотри в [общих справочниках](../../references/index.md).

Если заказан только список кейсов, остановись после тест-дизайна. При запросе на проверку выполняй доступные тесты. Добавляй или меняй тестовые файлы, когда это входит в задачу либо в утверждённый план. При самостоятельной проверке верни пользователю дефекты и способы воспроизведения и закончи на этом. В полном цикле передай тот же результат координатору для исправления разработчиком. При отсутствии однозначного требования проверь известную часть и выдели вопрос владельцу контракта.

Если способы проверить критичную гарантию дают существенно разную достоверность или требуют разной инфраструктуры, подключи советника по [правилам обращения](../devrelay-python-advisor/rules/consultation.md). В отчёте укажи его рекомендацию и отдельно перечисли фактически выполненные проверки.

При изменении формата примени [проверку совместимости при выкладке](../../references/common/rollout.md). Воспроизведи сохранённый старый вход и достижимые смешанные версии через реальную границу проекта. Если нестабильный отказ мешает проверке, приведи отличия успешной и неудачной попыток. При необходимости можно подключить [диагноста](../devrelay-python-diagnostician/SKILL.md).
