# Как сверять постановку с проектом

## Выдели наблюдаемый результат

Для каждого условия назови участника, действие и эффект. Фраза «повтор события успешен и письмо уходит один раз» содержит как минимум два требования. Ответ API и количество отправок могут изменяться независимо. Сохраняй исходные названия полей и статусов.

## Найди действующий путь

Начни с регистрации маршрута, команды или задачи. Проследи один конкретный вход до ветвления, чтения или записи и формирования ответа. Найди ближайший тест и потребителя результата, когда от него зависит совместимость. Для поля проверь модель запроса, преобразование аргументов, хранилище и схему ответа. Для фоновой задачи установи, кто её ставит и что считается успешной обработкой.

Подтверждай вывод файлом и именем символа, тестом или воспроизводимым наблюдением. Прочитанный тест фиксирует ожидание автора. Успешный запуск подтверждает результат в указанном окружении. Если модель объявляет уникальность, а миграции или живая схема недоступны, укажи, какую часть удалось проверить.

| Результат сверки | Что предъявить |
|---|---|
| Реализовано | Рабочий вызов и покрытая часть результата. |
| Требуется изменение | Вход, текущее поведение, желаемый результат и затронутый потребитель. |
| Неоднозначно | Возможные исходы с разными последствиями. |
| Не удалось подтвердить | Что просмотрено, каких данных не хватает и как это влияет на вывод. |

При нескольких реализациях выясни, какая зарегистрирована для нужной версии API, задачи или конфигурации. Соседний обработчик полезен как аналог, но может иметь другой контракт.
