# Реализация в границах поручения

1. Открой ближайший рабочий аналог, места сборки зависимостей и вызовы изменяемого кода. Возьми версии Python, библиотек и команды проверок из проекта. Учитывай ограничения пользователя и изменения, которые уже лежат в рабочем дереве.
2. Внеси самое узкое изменение, полностью покрывающее согласованный контракт. Если фиче нужны две точки входа, проверь, кто преобразует внешний формат и где должна единожды выполняться общая операция. Технические детали выбирай по справочнику соответствующего стека.
3. Реализуй ошибки и повторные вызовы вместе с успешной веткой, если они входят в контракт. При изменении нескольких записей проверь, кто выполняет коммит. Если старые данные встречаются на рабочем пути, сохрани их поддержку или выполни согласованный переход.
4. Проверь изменённую функцию через её обычного потребителя. Прогони ближайшие существующие тесты и нужные проверки проекта. Для нового поведения добавь тест, если его требует план, правила проекта или он ловит конкретную регрессию. Тестировщик получит возможность независимо проверить полноту покрытия.
5. Перед передачей прочитай собственные изменения целиком, включая новые файлы, конфигурацию и обновлённые ожидания тестов. Когда сборка не запускается, зафиксируй точную команду и причину. Отдели дефект реализации от проблемы окружения.

Например, при частичном обновлении поля проверь вызов сериализатора и операцию записи. Сохранение пропущенного поля может быть реализовано на HTTP-входе и снова сломано глубже при конструировании модели с дефолтами. Один успешный ответ API не проверяет сохранённую строку.
