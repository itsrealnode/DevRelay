# Самопроверка перед передачей на ревью

До первой правки выбери из справочников правила, от которых зависит обычный путь этой задачи. Для каждого значимого решения назови вход и наблюдение, которое отличает правильную реализацию от внешне похожей ошибки. После реализации проверь собственный diff, включая новые файлы, и прогони эти наблюдения до передачи независимому ревьюеру.

| Где меняется код | Вопрос перед написанием | Свидетельство при передаче |
|---|---|---|
| Список, экспорт, сериализация связей | [Какие строки и связи нужны потребителю?](../../../references/common/collections.md) | Ожидаемые ID и порядок, число обращений при росте коллекции. Для страницы проверь границу, для полного списка проверь отсутствие усечения. |
| Новый класс, сервис или общий метод | [Кто уже владеет операцией?](../../../references/common/architecture.md) Что изменится у двух действующих вызывающих сторон? | Обычный вызов и конкретная обязанность слоя. При объединении похожего кода проверь границы, на которых поведение потребителей различается. |
| Формат сообщения, поля API или БД | [Какие версии встретятся при выкладке?](../../../references/common/rollout.md) | Фактический пример старых данных с новой версией и обратное сочетание, если оно достижимо. |
| Несколько записей или повторная команда | [Какие изменения вступают в силу вместе?](../../../references/common/consistency.md) | Ответ при повторе, состояние БД после сбоя и число побочных эффектов. |

Сверь объём изменения и критерии с прямым поручением или одобренным планом. Исправь найденный дефект и перепроверь затронутый путь в границах поручения. Сообщи пользователю или координатору, какие команды или замеры выполнил и что осталось непроверенным. Для локального изменения чистой функции достаточно подходящих примеров входа и выхода.
