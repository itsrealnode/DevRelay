# Проверяй решение на конкретных путях

| При каком изменении | Куда посмотреть | Какое нарушение искать |
|---|---|---|
| Поля API или сериализация | Модель входа, преобразование, запрос к хранилищу, модель ответа | Пропуск, явный null или допустимое пустое значение слились в один исход. Данные, возвращённые клиенту, отличаются от сохранённых. |
| Доступ к ресурсу | Точки входа и фактический фильтр чтения или обновления | Одна точка входа соблюдает согласованную область видимости, другая обходит проверку. |
| Несколько изменений в БД | Кто открыл транзакцию, когда происходит commit, где ловится исключение | Ранний commit оставляет запись при сбое последующей операции. Ошибка сохранения теряется за успешным ответом. |
| Повтор или конкуренция | Ключ уникальности, условие обновления, записи истории и постановка задач | Последовательный повтор проходит, но две одновременные попытки обе создают эффект. |
| Изменение типов или зависимостей | Сигнатура вызывающего кода и обе реализации контракта | Подмена принимает аргументы или возвращает варианты, которых нет у рабочего адаптера. |
| Асинхронный маршрут | Реальный драйвер ввода-вывода | Синхронный вызов блокирует поток обработчика. |

Выбирай строки, относящиеся к изменению. Техническое замечание подкрепляй входом и следствием. Для архитектурного замечания покажи, где сейчас нарушается граница или появляется дублирование бизнес-правила. Само по себе предпочтение класса, слоя или паттерна не доказывает дефект.

Изучи и тесты. Подмена, которая заранее возвращает нужное значение независимо от аргументов, способна скрыть потерю поля. Проверь, какое изменение в реализации заставило бы тест упасть. Если код очевидно нарушает контракт, для замечания достаточно строгого разбора пути. При доступном окружении короткое воспроизведение усиливает вывод.

## Большие функции и методы

Прочитай изменённый метод целиком. Выдели действия, которые меняются по разным причинам. Например, импорт может разбирать строки, рассчитывать стоимость и сохранять результат в одной транзакции. Если из-за этого проверка скидки требует поднять БД и собрать файл импорта, предложи выделить конкретный расчёт. Укажи его входы, результат и тест, который можно будет выполнить отдельно. Владение транзакцией и порядок записи оставь явными у вызывающего сценария.

Длина и вложенность помогают выбрать место для чтения. Для замечания покажи полезную границу: какое правило получит своего владельца, какую ветку станет проще проверить или какую ошибку предотвращает разделение. Если длинный метод описывает один последовательный переход, а предполагаемая разбивка заставляет передавать изменяемый контекст между пятью помощниками, сохрани целостный сценарий. Улучшение читаемости пометь как рекомендацию. Для дефекта укажи нарушенный контракт.

## N+1 при обработке коллекций

Проследи обычный вызов до конца сериализации по [общему правилу загрузки коллекций](../../../references/common/collections.md). Покажи место повторного обращения, форму SQL и изменение числа запросов между размерами выборки. Если проверял чтением, опиши цепочку до обращения в БД. При повторном ревью сверь исходные результаты, включая строки с пустыми связями.

## Дублирование логики

Ищи совпадения по смыслу: одинаковый расчёт, условие допуска, переход статуса, сборка запроса или преобразование входа. По изменённому правилу найди другие точки входа, включая задачи, команды и соседние сервисы. Для замечания приведи минимум два конкретных места и назови правило, которое приходится менять синхронно.

Сравни входы, поведение на границе и причины возможных изменений. Например, API и задача рассчитывают одну скидку, но только задача включает покупку ровно на сумму порога. Приведи пограничный вход, проверь согласованный исход и предложи общего владельца расчёта. Если копии пока совпадают, опиши риск расхождения как рекомендацию. Формат ответа API и поведение задачи при ошибке могут остаться у своих точек входа.

Похожий запрос администратора и пользователя может выражать разную политику доступа. Прежде чем предлагать общий помощник, проверь, что изменение одного правила действительно должно затрагивать оба места. При повторном ревью проверь оба вызова на обычном и пограничном входах.

## Неограниченные выборки

Для каждого изменённого чтения коллекции найди место материализации по [общему правилу ограничения выборки](../../../references/common/collections.md). Для страницы сравни запрошенный размер с фактически загруженным объёмом. Для существующего полного списка проверь, сохраняются ли все элементы и добавляет ли изменение новую нагрузку. Если растущая неограниченная выборка уже существует, укажи место и последствия отдельно от дефекта новой реализации. Само отсутствие пагинации у обёртки над таким контрактом не является дефектом. Для полного экспорта укажи, где растёт память до записи результата.

## Лишние промежуточные слои

Проследи действующий вызов по [общему правилу границ ответственности](../../../references/common/architecture.md). Укажи оба метода, потребителей, ответственность слоя и проверку сохранения поведения после упрощения. При равном поведении оформи упрощение как рекомендацию. Если обход слоя меняет ответы, права или границы отката, покажи соответствующий сценарий до предложения об удалении.
