# Определи границы ревью

Для PR выясни базовую и проверяемую версии. Для локальной работы посмотри staged, unstaged и новые файлы по задаче. Если дан конкретный модуль без истории изменений, проверь текущую реализацию и обозначь этот объём. Не приписывай новой правке старый дефект без основания. Старое поведение важно, когда изменение теперь делает его достижимым либо нарушает утверждённый критерий.

Прочитай исходное требование и подтверждённые ответы. Если передан отчёт разработчика, возьми из него команды и точки входа. Самостоятельно найди реальных потребителей изменившихся функций и схем. Если тест одним изменением заменил старое ожидание на новое, проследи это ожидание до пункта постановки.

Для каждого существенного изменения спроси: какой результат увидит вызывающий код на успехе, при отказе и при повторе? Если публичный контракт изменён намеренно, проверь согласованность обработчика, документации интерфейса, клиентов в репозитории и тестов в пределах задачи. Для простой локальной функции хватит затронутых вызовов и границ входов.

Перед завершением сопоставь изменения с критериями. Пропущенную обязательную часть укажи даже тогда, когда существующие тесты зелёные. При отсутствии исходного контракта можно доказать технический дефект, например гарантированное исключение на поддерживаемом входе. Неопределённое бизнес-поведение обозначь вопросом.
