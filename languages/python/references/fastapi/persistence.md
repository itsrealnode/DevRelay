# Хранение данных и граница транзакции

Для создания и поиска по UUID смотри [репозиторий SQLAlchemy](examples/sqlalchemy_repository.py). Он преобразует ORM-запись в доменную сущность и возвращает `None` при отсутствии записи. Транзакцией управляет [UoW](examples/uow.py), выходной DTO собирает [use case](../common/examples/use_case.py).

Начни с вызова, который нужен сценарию. Проверь, покрывает ли его существующий запрос. Для нового метода согласуй сигнатуры реализации, интерфейса и тестовой подмены. Если модуль уже работает через ORM напрямую, вводи репозиторий только для конкретной потребности сценария.

- **Чтение.** Определи количество результатов и смысл отсутствия. Проверь известный и неизвестный ключ. Если результат используется после закрытия сессии, проверь доступ к нужным полям в этот момент.
- **Запись.** Выбери результат по потребителю: обновлённые данные, признак перехода или разные причины отказа. Для PostgreSQL и SQLAlchemy условный `UPDATE … RETURNING id` может одновременно захватить открытую заявку и сообщить, состоялся ли переход.
- **Транзакция.** Проследи, кто создаёт сессию и кто подтверждает операцию. Если проект использует Unit of Work, передай всем участникам его сессию. Для получения ID до коммита используй `flush()`, если это соответствует способу работы проекта. Внутренний метод репозитория должен позволять откатить запись снаружи. При отказе коммита успех не должен уйти клиенту.

**Пример проверки.** Когда двое одновременно берут открытую заявку, операция добавляет историю только после успешного условного обновления и в той же транзакции. На двух соединениях проверь одного исполнителя и одну запись истории. Если API обязан различать «заявка не найдена» и «уже занята», простой признак обновления не выражает весь контракт. Проверь оба исхода.
