# Типы, состояния и ошибки

Выбирай форму результата по решениям вызывающего кода. Сверь типы, имена аргументов, ожидаемые исключения и смысл отсутствующего значения с ближайшим аналогом.

| Что должен различить потребитель | Подходящий контракт |
|---|---|
| Действие состоялось или нет, дополнительных данных нет | Верни `bool`, если все причины отрицательного ответа для потребителя равнозначны. |
| Найдена запись по уникальному ключу | Следуй принятой семантике отсутствия, например `Ticket | None` или предметному исключению. Для коллекции обычно подходит пустая последовательность. |
| Импорт удался с ID или отклонён с причиной | Опиши отдельные варианты `Imported(record_id)` и `Rejected(reason)`, чтобы обязательные данные сопровождали свой исход. |

В новом модуле вырази ожидаемый бизнес-отказ типизированным результатом, когда вызывающий код выбирает следующий шаг. Например, `Assigned` и `CapacityReached` могут вести к разным ответам API. Если аналог уже задаёт предметное исключение, сохрани его для существующих потребителей. Сбой соединения или коммита должен дойти до кода, который умеет восстановиться либо сообщить о техническом сбое. Сохрани причину при переводе исключения адаптером.

Проверяй внешний JSON при разборе. Аннотации Python описывают контракт для инструментов и разработчика. Для изменённой операции проверь успешный исход, предусмотренный отказ и значимые побочные эффекты каждого. Проверь совместимость типизатором проекта, если он настроен.
