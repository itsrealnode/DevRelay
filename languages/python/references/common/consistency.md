# Атомарность, повторы и конкуренция

1. Назови изменения, которые должны сохраниться вместе. У владельца операции должна быть одна транзакция для всех таких записей. Проверь сбой между записями и состояние после отката из нового соединения.
2. Раздели повтор одной команды и второе законное действие. Уточни ключ, область уникальности и ответ на повтор. Для входящего события ключ может определяться парой «источник + внешний ID», если именно так определена идентичность события. Учитывай уже сохранённые данные при введении ограничения.
3. Закрепи инвариант там, где его видят все исполнители. Уникальность пары удобно обеспечить ограничением БД. Для перехода из известного состояния подходит условное обновление. Для лимита по нескольким строкам определи, какой общий объект сериализует конкурирующие изменения.
4. Определи, можно ли потерять внешний эффект после коммита. Если доставка обязательна, сохрани задание на отправку в транзакции с бизнес-изменением, предусмотрев повторную отправку и защиту получателя от дублей.

**Проверка на примере назначения.** Вызови команду дважды, как при потере первого ответа. Проверь не только число назначений, но и число записей истории или отправленных уведомлений. Для гонки запусти две попытки через разные соединения на рабочем типе БД. Если транзакция назначения откатилась, проверь видимое состояние и возможность повторить операцию.
