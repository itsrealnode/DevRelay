# Форма кода и общие компоненты

Начни с обычного вызова операции в месте её использования. Определи, откуда приходят данные, кто владеет состоянием и используются ли зависимости дольше одного вызова.

| Ситуация | Выбор |
|---|---|
| Результат целиком определяется явными аргументами | Напиши функцию. Для нормализации кода направления достаточно строки на входе и строки на выходе. |
| У существующего объекта есть состояние и правила его перехода | Добавь метод владельцу состояния. Если закрытие заявки меняет статус и дату, собери этот переход в одном месте. |
| В новом модуле у операции одна зависимость и два потребителя | Начни с функции вроде `assign_direction(repo, ...)`. HTTP и фоновая задача вызывают её со своими входными данными. |
| Соседние сценарии получают долгоживущие зависимости при сборке или управляют ресурсом | Следуй принятой форме объекта операции. Передай зависимости при создании, данные конкретной команды — в `execute()` или `__call__()`, как в соседнем сценарии. |

## Куда положить общий компонент

Посмотри, откуда соседние модули импортируют общие типы и функции. Проверь `commons`, `common` или `shared` и переиспользуй подходящий контракт. Когда задача впервые вводит соглашение для всего проекта, положи его в принятый общий пакет уже при первом использовании. Если пакета нет, создай `commons` с модулем по назначению.

Например, общий формат страниц `items` и `total` может жить в `commons/pagination.py`. Фильтр доступных сотруднику заявок оставь у заявок даже при нескольких маршрутах-потребителях. Проверь направление импорта: общий пакет должен использоваться фичей без обратной зависимости от неё.

## Константы и перечисления

Сначала определи, какому модулю принадлежит значение, и посмотри, где в проекте объявлены аналогичные константы и перечисления. Переиспользуй существующее определение, если оно выражает то же правило.

По умолчанию помещай именованные константы в `constants.py` соответствующего модуля, а классы перечислений в его `enums.py`. Например, лимит повторов оплаты `MAX_PAYMENT_ATTEMPTS` объяви в `payments/constants.py`, а статусы оплаты `PaymentStatus` в `payments/enums.py`. И API, и фоновый обработчик могут импортировать эти определения из `payments`.

Сложившаяся архитектура проекта имеет приоритет. Например, если статусы Django-моделей в этом приложении объявляют через вложенные `TextChoices`, добавь новое перечисление по тому же образцу. При ревью обоснуй выбор места владельцем значения и ближайшим аналогом в проекте.
