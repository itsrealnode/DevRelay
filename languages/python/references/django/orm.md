# Django ORM

**Базовая модель.** При добавлении модели посмотри, от какого класса наследуются соседние модели с такими же требованиями к полям. Если в проекте уже есть подходящий абстрактный класс, наследуйся от него. В [примере](examples/models.py) обе модели наследуют `created_at` и `updated_at` от `BaseAbstractModel`. Django добавляет каждой модели поле `id` с типом из настройки приложения или проекта. При изменении строк через `QuerySet.update()` передай `updated_at` явно, если поле должно отражать эту операцию.

**Назначение по уникальному ключу.** Сначала найди ограничение модели и соответствующую миграцию. При `get_or_create()` передавай поля ключа как аргументы поиска, а остальные начальные значения — в `defaults`. Например, для выдачи направления это может быть `Assignment.objects.get_or_create(mentor_id=mentor_id, direction_id=direction_id)`. При конкурентных вставках опирайся на ограничение уникальности этой пары в БД. Если его предстоит добавить, проверь существующие дубли и включи их обработку в план.

**Чтение списка.** Проследи, какие связи реально читает сериализатор или шаблон. Для одиночной связи рассмотри `select_related()`. Для обратной связи или коллекции используй `prefetch_related()`, если его результат используется при сериализации. Посмотри, не выполняется ли дополнительный фильтр в цикле, который снова обращается к БД.

**Проверь** число запросов на всей выдаче с одной и несколькими строками и заполненными связями. Включи в измерение вычисление ленивого QuerySet и сериализацию. Для общего фильтра доступа, принадлежащего приложению, переиспользуй его существующий QuerySet или менеджер.
