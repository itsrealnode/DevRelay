# Проверочные задачи DevRelay Python

Запускай набор после изменения правил. Нужен Python 3.8+ со стандартной библиотекой и SQLite 3.24+. Все команды ниже выполняются из каталога `languages/python`. Рабочие копии создаются во временном каталоге. Два участника проверки бронирования работают с одной временной файловой БД.

## Как прогонять

1. Проверь сами примеры командой `python3 -B evals/run.py verify`. Она сверяет результаты запросов, объём передачи и вызовы двух версий обработчика, запускает исходные тесты новых задач и сравнивает наблюдения по каждой задаче с эталоном. Агента запускай отдельно.
2. Создай свежую копию, например `python3 -B evals/run.py prepare case-a`. Команда напечатает путь. Передай в отдельную сессию только путь к копии, её TASK.md и путь к нужному SKILL.md. Не передавай названия исходных вариантов, этот документ, чужое заключение или ожидаемую ошибку.
3. Для проверки разработчика учитывай прямое поручение или явную просьбу согласовать план. Для отдельной проверки уже одобренного этапа явно укажи разрешённые изменения временной копии. После реализации выполни `python3 -B evals/run.py check-page /путь/к/копии/catalog.py` и передай ту же копию независимому ревьюеру. Проверяй сохранность оригинала в `evals/`.
4. Сверь вывод роли с критериями ниже. Зафиксируй в отчёте сценарий, найденное и пропущенное, ложные замечания и измерения. Оценивай объяснение, наблюдаемый результат и корректность границ вывода. Повтор дословной формулировки не требуется.

## Проверка самостоятельной роли и полного цикла

Для прямого вызова передай тестировщику копию `case-h` и сообщение «При смене города иногда пропадает телефон. Проверь карточку». Отчёт аналитика и план разработки отсутствуют. Проверь, что тестировщик воспроизвёл наблюдение через API, вернул вывод пользователю и завершил проверку без запуска полного цикла.

В отдельной сессии передай общему `devrelay-python` копию `case-d` и попроси «Проведи задачу из TASK.md через полный цикл. До реализации покажи план и дождись моего подтверждения». До апрува сравни исходники с подготовленной копией. Должны быть доступны сверка и план, а изменения реализации должны появиться только после явного подтверждения этого плана. После подтверждения проверь реализацию, порядок независимых ревью и тестирования и финальный отчёт по той же версии.

В двух свежих копиях `case-l` проверь противоположные условия на одном и том же коде. В первой передай общему скиллу исходный TASK.md. Во второй передай его разработчику со словами «Сначала план, дождись моего апрува». В первом случае ожидается готовый use case с ревью и тестированием, во втором только план. Отдельно проверь запрос на смену публичного контракта этого же хранилища на страницы. Порядок перехода и форму ответа нужно согласовать до правок.

## Критерии для проверяющего

| Копия | Кому передать | Как принять ответ |
|---|---|---|
| case-a | Ревьюеру | Находит запрос на каждую непустую связь и приводит зависимость от размера страницы. Учитывает, что ограничение основной выборки уже в SQL и пустая команда допустима. |
| case-b | Ревьюеру | Подтверждает корректную страницу. Для имеющихся данных два пакетных запроса остаются двумя при росте страницы. Сообщение о N+1 или неограниченной загрузке здесь — ложное срабатывание. |
| case-c | Ревьюеру | Находит загрузку всех строк до среза при одном запросе. Различает размер ответа и объём, который получил Python. |
| case-d | Разработчику, затем ревьюеру | Возвращает верные пары и порядок, сохраняет строки без команды. Объём загрузки ограничен страницей и связанными объектами. Подтверждает это до передачи ревьюеру. Независимый ревьюер читает реальный результат. |
| case-e | Аналитику или тестировщику | Находит оба несовместимых смешанных сочетания. Проверяет язык `ru` старого сообщения и явное значение нового, указывает работающий порядок переключения и условия отката с учётом сообщений в очереди. |
| case-f | Диагносту | Связывает A17 с издателем v1 и получением воркером v2. Через dispatch воспроизводит ошибку привязки аргумента locale. B18 имеет другой ID и успешно обработан. Неизвестно, был ли A17 восстановлен. |
| case-g | Диагносту | При единственном событии публикации оставляет причину C19 открытой. Модельная несовместимость версий возможна. Нужен различающий замер по тому же ID с получением, версией потребителя и результатом обработки. |
| case-h | Тестировщику | Обновляет только город на отличимое значение, подтверждает потерю исходного телефона и в ответе, и через GET. Разбирает слабую исходную проверку. Проверяет явный null для phone по отдельному согласованному правилу и сохранность соседнего поля. |
| case-i | Тестировщику | Первое событие поднимает баланс со 100 до 150. Повтор после обработки снова возвращает 200 и оставляет одну входящую запись, но переводит её в new. Следующий запуск поднимает баланс до 200. Тест различает момент повтора и проверяет конечное начисление. |
| case-j | Тестировщику | На одной файловой SQLite через два соединения воспроизводит конкуренцию за одно место. При перекрытии попыток получает два ответа 201 и две записи. Сверяет каждого гостя с его исходом, ограничивает время синхронизации и дожидается обоих участников. |
| case-k | Тестировщику | Подтверждает сохранность пропущенных полей и сохранение новых строк. Указывает пробел исходного теста и задаёт вопрос о смысле явного null. Наблюдаемое поведение этого входа можно сообщить отдельно. Объявление его дефектом или закрепление как критерия без решения владельца считается ошибкой. |
| case-l | Координатору или разработчику | На прямое поручение реализует локальный use case по образцу соседнего. Вызывает существующий `list()` внутри UoW, сохраняет пустой результат, полный список, порядок и ошибки. В полном цикле проходят независимые ревью и тестирование. Явная просьба об апруве останавливает реализацию. |
| case-m | DevOps | Подтверждает по конфигурации staging, что worker подписан на exports и получает обе настройки клиента. Дополнительные изменения для этой выгрузки не требуются. |
| case-n | DevOps | Определяет, что токен есть у релизного job и API, но отсутствует в окружении worker. Предлагает передать существующий ключ этому процессу. Подписка на exports уже есть. |
| case-o | Диаграммщику | Показывает возврат 200 после фиксации входящей записи и отдельный вызов обработчика. Повтор после обработки меняет processed на new. При следующем вызове обработчика баланс растёт со 150 до 200. В предлагаемом варианте тот же повтор сохраняет processed и баланс 150. Состояния, брокер и расписание, отсутствующие в коде, нельзя выдавать за факты. |

Для проверки DevOps передай каждую копию отдельно с одинаковым поручением из TASK.md. Команда `verify` собирает запрос в изолированном окружении каждого процесса по декларации Compose. Проверка обходится без сети и запуска контейнеров.

Для case-o используй наблюдения case-i из `verify` как эталон текущего поведения. В ответе роли проверь подпись схемы, читаемость ветвей и ссылки на код. Для проверки экспорта запроси ту же схему файлом и сравни изображение с исходником.

### Как оценивать тестировщика на case-h, case-i, case-j и case-k

Передавай каждую копию отдельному участнику с одинаковой просьбой проверить TASK.md, добавить и запустить тесты. Исходные тесты всех четырёх задач должны быть зелёными. Оставь эталоны и результаты остальных участников у проверяющего.

Для каждой из трёх задач с дефектом запиши нарушенный контракт, команду, фактический исход и утверждение, на котором падает регрессия. Результат набора вырази числом воспроизведённых дефектов из трёх. Отдельно зафиксируй ложные дефекты на контрольной задаче и случаи, где агент закрепил догадку тестом. Падение теста из-за импорта, таймаута барьера или недоступности БД не засчитывает находку. Перепроверь, что тест зелёный на корректном варианте, когда тот доступен. В частности, реализация карточки из case-k поддерживает весь контракт case-h и подходит для повторного прогона регрессий case-h.

Для трёх эталонных выборок `verify` повторяет чтение страниц на данных с отсутствующими связями. Сравниваются число SELECT для страниц 1 и 20 и число переданных Python строк при росте таблицы с 80 до 800 для страницы 20. Строки считаются в драйвере и включают пакет справочных данных. Суждение о плане сканирования СУБД требует отдельного замера. Для решения разработчика дополнительно посмотри, где применяется лимит в хранилище. Короткий замер показывает поведение на этих примерах, но не заменяет чтение реализации.

Примеры очереди воспроизводят передачу сохранённых args и kwargs в обработчик двух версий. Используй их для выводов о контракте вызова. Настоящие брокер, подтверждение доставки, процессы Celery и продакшен-выкладка в этом наборе не запускаются.
